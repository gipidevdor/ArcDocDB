# Publishing the manual

The online manual is generated by [CommonDoc Codex](https://github.com/CommonDoc/codex),
the Common Lisp documentation generator. The repository's Markdown files remain
the authoritative source. There is no second hand-maintained copy of the manual.

## Read and navigate

The site presents the complete documentation in seven collections: getting started,
implementation, architecture and design, architecture decisions, reliability and
evidence, experiments and reference, and publication and project information. The original specification and design
analysis are included in full. Each document keeps its existing path with an
`.html` extension; explicit legacy anchors remain available.

The home page and selected navigation provide short reading paths. The complete
index lists every published document. Search covers page titles, paths and the
full text, including identifiers. It runs in the browser without sending queries
to a service. Reading, links and the complete index work without JavaScript;
search, appearance preferences and rendered Mermaid diagrams enhance them.

Implementation and design keep their own scope. Publishing a design document
does not qualify its guarantees or claim that the full engine is implemented.

## Build and preview

Use SBCL, Git, `curl`, `tar`, `find` and `shasum`. The supported CI compiler is
SBCL 2.6.9. Internet access is required for the first dependency download.
The optional local preview command uses Python 3's standard HTTP server.

```sh
make docs
make docs-serve
```

Open `http://127.0.0.1:8765`. `make docs` creates the complete static artifact in
`_build/site/`. Dependencies, downloaded archives and the compiled cache stay
under `_build/docs/`. Both directories are ignored by Git. The product's build
and runtime dependencies are unchanged.

The documentation process has an explicit default dynamic-space budget of
2,048 MiB (`DOCS_DYNAMIC_SPACE_SIZE`). The verifier releases each page's DOM
after extracting its links and anchors; it does not retain the full HTML corpus
as DOM trees during repeated negative checks. This is a build-tool budget, not
a database memory setting or an RSS guarantee.

For subsequent builds, `make docs-check` reuses installed documentation
dependencies and performs the same rendering and publication checks.
`make docs-build` renders without running those additional checks.

## How Codex builds the site

1. The bootstrap verifies every downloaded archive against
   [`dependencies.lock.lisp`](../tools/pages/dependencies.lock.lisp). It installs
   a private ASDF source tree without updating the user's Quicklisp installation.
2. The Lisp builder inventories Markdown documents, renders them with 3bmd and
   prepares a generated Scriba document and Codex manifest.
3. A CommonDoc macro inserts each original document. `codex:document` expands
   those macros and emits pages through the project's registered HTML template.
4. The builder publishes stable paths, rewrites document links, preserves explicit
   anchors, copies image assets and writes the local search index and sitemap.
5. Verification checks source coverage and SHA256 hashes, search coverage, one
   main heading per page, unique IDs, local files, anchors and artifact structure.
   A missing source document or unresolved link fails the build.
6. Editorial checks screen prose for selected language and numeric-style defects.
   Publication gates verify local search behavior, labels, image alternatives,
   diagram descriptions, declared contrast pairs and byte-exact license notices.

The [editorial policy](editorial-policy.md) defines the language and preservation
rules. [Publication information](legal/README.md), [privacy](legal/privacy.md),
[third-party notices](legal/third-party.md) and [accessibility](legal/accessibility.md)
are linked from every page. These checks do not certify legal or WCAG compliance.

Bootstrap, generation, regression checks and publication verification are Common
Lisp scripts. [ADR-0075](adr/0075-codex-documentation-toolchain.md) scopes the
requested external generator and browser assets to documentation only.
The storage engine is never loaded to generate its manual. Code and raw evidence
links lead to the matching GitHub source revision. Raw `spikes/results/` files and
GitHub issue/PR templates are excluded from the published document collection;
the documentation's links to those files remain available on GitHub.

Codex is archived upstream. Its 2024-10-12 release, the documentation dependency
closure from Quicklisp 2026-01-01 and Mermaid 11.12.1 are fixed by SHA256. Refresh
the lock deliberately and run the full documentation checks when updating them.
The static site serves its own scripts and stylesheet and uses system fonts;
diagram rendering does not depend on a CDN.

## GitHub Actions and first publication

The [Documentation workflow](../.github/workflows/docs.yml) builds relevant pull
requests and uploads the verified Pages artifact. Pull requests cannot deploy.
Pushes to `main` and manual runs on `main` publish that artifact through the
`github-pages` environment. Builds receive `contents: read`; only deployment
receives `pages: write` and `id-token: write`. No personal access token is needed.

For the first publication, select **Settings → Pages → Build and deployment →
Source → GitHub Actions** in the repository. Push the workflow to `main`, or run
**Actions → Documentation → Run workflow** after enabling Pages. The deployment
job reports the actual published URL.

The default canonical address is `https://gipidevdor.github.io/ArcDocDB/`.
For a custom domain or fork, set the repository variable `DOCS_SITE_URL` to its
absolute HTTPS address, including the trailing slash. The same variable can be
set locally. Relative document and asset links support project-path hosting.

Generated HTML is an artifact, not a committed branch. Failed builds leave the
last successful deployment available. To roll back a published edition, run the
workflow against the desired repository state on `main` through the normal Git
revert process; no parallel documentation history is needed.

## Visual and editorial rules

The site follows the [repository's visual language](../assets/README.md): system
type, restrained ink and graphite, generous space and amber for mutable state.
Navigation serves the reader's question. Original titles, contracts, caveats and
evidence remain intact. There are no analytics, remote fonts or marketing claims
about unqualified performance. Layouts support mobile reading, keyboard access,
light and dark appearance, reduced motion and printing.

The presentation lives in `tools/pages/theme.lisp`, `site.css` and `site.js`.
Curated navigation and collection rules live in `tools/pages/model.lisp`.
Adding a Markdown document automatically adds it to the collection and search.
